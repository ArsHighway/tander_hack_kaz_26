# Справочник из стандартов категорий портала

> Срез на дату документа. С 11.10.2026 модель — локальная `gemma-4-31b-it-Q8_0.gguf` в llama.cpp server, Ollama и облачные ключи в решении не используются ([model-choice.md](../model-choice.md)); упоминания Ollama, облачных квот и `gemma4:31b` ниже описывают состояние на тот день.

Цель: заменить синтетический `demo.json` справочником на все конечные категории товаров портала:
состав характеристик — из стандарта категории (`data/standards/standards.jsonl`, `fetch_standards`),
допустимые значения — из живых СТЕ (`data/ste_full/ste.jsonl`, `fetch_ste --per-category 0`).
Выход — JSON для `Catalog.load` (`CATALOG_PATHS`), конвейер не меняется.

Замер на 600 стандартах и 283 тыс. СТЕ (06.10.2026): ~120 характеристик на категорию, из них
официальных 6 %, обязательных ~2; 30 % диапазонов — заглушки; 923 записи единиц; значения СТЕ
связываются с шаблоном по `char_id` в 94 %, по базовой характеристике 2,2 %, по имени 2,4 %.

## Решения

- Позиция = конечная категория портала. Код — код КПГЗ категории; если он повторяется у
  нескольких категорий — `<код>/<id категории>`, чтобы `Catalog` не падал на дубле.
- Характеристика попадает в позицию, если она официальная (у строки шаблона есть `isObligatory`,
  ссылка на КТРУ или СПГЗ, `isLevelDefine` или базовая характеристика) и заполнена хоть у одной СТЕ
  либо обязательна; добавленная поставщиком — только при доле заполнения в категории
  `>= min_share` (по умолчанию 0,3, как у `portal.catalog.build_positions`). Без порога в каждой
  категории 100+ разовых полей.
- Строки шаблона с `deleted: true` отбрасываются.
- Тип: 1 целое, 2 дробное → `quantitative` (единица, диапазон без заглушек); 4 признак →
  `qualitative` с «Да»/«Нет»; 5 справочник, 6 текст → `qualitative`, перечень из СТЕ.
- Перечень: значения, встретившиеся у `>= min_value_cards` СТЕ, склейка написаний как в
  `ValueIndex` (`value_key`, опечатки к частому), не больше `max_values`; характеристика с
  числом разных значений больше `max_values` — свободный текст (`values: []`, `fit_value`
  принимает любое).
- Связь значения СТЕ с характеристикой: `char_id` = id характеристики, id синонима или базовой;
  затем совпадение имени (`fold`). Непривязанное — в отчёт.
- Синонимы имени (`productCharacteristicSynonyms`, `productCharacteristicNameSynonymsJson`) и коды
  КТРУ/СПГЗ сохраняются в спецификации: понадобятся извлечению и цепочке ОКПД2 → КТРУ.
- Значения накапливаются потоком по jsonl (1,35 млн СТЕ не держим в памяти); у характеристики не
  больше `MAX_TRACKED` разных значений, дальше — свободный текст.

### Task 1: модель

`CharacteristicSpec` + `synonyms: list[str] = []`, `ktru: list[str] = []`, `spgz: list[str] = []`;
`Position` + `kpgz: str | None = None`. Старые JSON читаются как раньше.

### Task 2: разбор стандарта — `app/portal/standards.py`

- `clean_bound(x) -> float | None`: `None`, `|x| >= 2147483647`, `|x| >= 1e14`, «девятки» от 5 цифр
  (999999, 99999.0) → `None`; 175 → 175, 99 → 99, 0.1 → 0.1.
- `canon_unit(raw) -> str | None`: части по «;» и текст в скобках через `normalize_unit`, берётся
  каноническая единица самой длинной распознанной части: «г; лет» → «лет», «Л; ДМ3» → «л»,
  «миллиметр (мм)» → «мм»; «[0*]С» → «°С»; нераспознанное — как есть.
- `parse_standard(rec) -> Standard` (id, path, name, root, kpgz, okpd2, chars по id): строки
  группируются по `productCharacteristicId`; у `StandardChar` — name, kind (int/decimal/bool/dict/
  text), unit, range, required, official, level_define, in_name, base_id, synonyms (имена) и
  synonym_ids, ktru, spgz, values (строковые значения шаблона, кроме ссылок справочника вида
  «1.2.3»).

### Task 3: значения из СТЕ — `ValueStats`

`add(sku)` по одной записи jsonl; `link(standard, char) -> char_id | None`; счётчики по
(категория, характеристика): СТЕ в категории, заполнено, значения (`value_key` → написания),
единицы. Тест: две СТЕ, связь по id, по синониму, по имени и непривязанная; доля, перечень с
`min_value_cards`.

### Task 4: сборка позиций — `build_standard_positions(standards, stats, ...) -> list[Position]`

Тесты: официальная редкая характеристика остаётся, поставщицкая редкая — нет, частая — да;
обязательная без значений остаётся; дубль кода КПГЗ получает суффикс; признак даёт «Да»/«Нет»;
заглушка диапазона не попадает; свободный текст — пустой перечень.

### Task 5: инструмент — `app/tools/build_standard_catalog.py`

`--standards`, `--ste`, `--out ../data/catalog/standards.json`, пороги. Пишет справочник и рядом
`*.report.json`: категорий, позиций, характеристик (официальных / добавленных), доля связанных
значений, топ непривязанных имён. Проверка: `Catalog.load` на результате, `evaluate` и
`portal_report --catalog` с ним.

## Итог (06.10.2026)

Сделано: задачи 1–5. Перечень или свободный текст решается до склейки опечаток (она квадратична):
сборка на 2070 стандартах и 624 тыс. СТЕ — 2,8 мин. Отчёт: 2062 позиции, 12,8 характеристики на
позицию (23 056 из стандарта, 3 322 добавленных поставщиками), 98,6 % значений СТЕ привязаны.

Прогон конвейера на этом справочнике (299 случайных СТЕ, только наименование, без LLM и векторов):
верная категория первой 30 %, в топ-5 41 %, «не найдено» 31 %, итоговый код без вопросов 9 %.
Это точка отсчёта для шага 3 (категория по похожим СТЕ): поиск по тексту позиции на 2 тыс.
категорий слаб.

## Синонимы характеристик по смыслу (08.10.2026)

Склейка по словам (`_merge_duplicates`) не видит пар без общих слов: «Плотность» и «Масса бумаги
площадью 1м2». Эксперимент `app.tools.find_synonyms` (решение пользователя: оба способа, один раз
при сборке справочника):

| Шаг | Что | Объём |
|---|---|---|
| `llm` | gemma4:31b, один вопрос на категорию | 8 084 из 8 158 категорий (74 так и не ответили по схеме), 8 222 пары |
| `embed` | bge-m3, косинус ≥ 0,8 внутри категории | 7 728 категорий, 63 307 пар |
| `check` | вето по СТЕ портала без отложенной выборки | против: 1 679 пар модели, 28 994 пары векторов |
| `judge` | модель подтверждает пары векторов, пачки по 30 | 31 530 пар (1 051 пачка), «одна» — 11 995 |

Первая версия `check` принимала пару по близким медианам и общим частым значениям — склеивала
«Высоту» с «Глубиной», «ввод» с «выводом», «Голосовое управление» с «Дисплеем» (у обоих «нет»).
Итог: данные только возражают (вместе в одной СТЕ с разными значениями, перечни без общих
значений, медианы вдвое врозь, разные величины), склеивается пара, про которую модель сказала
«одна». Имена без предмета («Тип», «Вид товара») не склеиваются.

Точность по ручной выборке 80 пар: пары модели — 97 %, пары векторов, подтверждённые моделью, —
около 90 % (ошибки: «Количество туб» и «флаконов», «Габариты упаковки» и «Габариты»).

Отложенная выборка (2 000 случаев, без LLM и векторов), справочник eval:

|---|---|---|---|---|---|
| база | — | 204 796 | 0,3858 | 0,0500 | 0,6191 |
| пары модели | 6 068 | 199 758 (−2,5 %) | 0,3865 | 0,0498 | 0,6115 |
| пары векторов | 14 119 | 194 407 (−5,1 %) | 0,3885 | 0,0518 | 0,6174 |

Метрики не сдвигаются (в пределах ±0,3 п. п.), выигрыш — меньше полей-дублей у поставщика.
Попутно найдено: правило «метка: значение» не смотрело на синонимы — после склейки поле
«Предназначение» оставалось пустым (исправлено, `b9a3bcc`; при равной метке имя важнее синонима —
`397635d`).

Квота: облачный ключ упёрся в «Free usage limit» на ~8,4 тыс. запросов (16:20); `judge` докончен
вторым ключом, 936 пачек без единого 429.
