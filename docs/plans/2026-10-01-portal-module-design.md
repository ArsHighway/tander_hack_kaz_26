# Модуль автозаполнения характеристик СТЕ для Портала поставщиков — дизайн

> Срез на дату документа. С 11.10.2026 модель — локальная `gemma-4-31b-it-Q8_0.gguf` в llama.cpp server, Ollama и облачные ключи в решении не используются ([model-choice.md](../model-choice.md)); упоминания Ollama, облачных квот и `gemma4:31b` ниже описывают состояние на тот день.

Дата: 01.10.2026. Статус: согласован с пользователем по частям в чате, спека — запись этих решений.

## 1. Зачем и что изменилось

Пользователь открыл собранный веб и увидел служебную страницу «Состояние системы», индикатор «Работает частично» и
слово «Эталон» в шапке. Решения пользователя:

- страницу состояния и индикатор убрать полностью: пользователю портала они не нужны;
- «Эталон» убрать: имя придумано агентом, ничего не говорит;
- решение подать как модуль, который Портал поставщиков (zakupki.mos.ru) встроит к себе, а не как отдельное
  приложение;
- всё делаем сейчас, до хакатона (бэкенд `/api/v1` и экраны на настоящем API), а не «прототип сейчас, бэкенд на
  хакатоне».

Основание. ТЗ: «Сервис разрабатывается для Портала поставщиков» (`docs/tz/01-methodology.md`), организатор внедряет
решения победителей (`docs/research/tenderhack-patterns.md` §4). Аналоги встраивают автозаполнение в существующую
форму карточки, отдельного приложения нет ни у кого:

- Яндекс Маркет: продавец вставляет текст любого формата, YandexGPT раскладывает его по полям характеристик; 93 %
  описаний сохраняют без правок;
- Amazon: по нескольким словам, фото или ссылке атрибуты предлагаются в форме листинга, каждый принять, поправить
  или отклонить; около 80 % принимают; есть пакетный режим через таблицу;
- Ozon: помощник в форме карточки заполняет характеристики по названию и фото;
- сам портал с июня 2026 заполняет характеристики по фото.

## 2. Решения, принятые в диалоге

| Вопрос | Решение |
|---|---|
| Как показать встраивание | Экран повторяет устройство формы «Создание СТЕ», наш блок внутри неё; вид наш (корректура из `DESIGN.md`), не копия портала |

| Когда | Всё сейчас |

## 3. Контракт API `/api/v1` (модуль)

Принципы:

- модуль ничего не пишет в данные портала: возвращает предложения, решение по каждому полю за человеком;
- у каждого значения — фрагмент исходного текста, у каждого замечания — правило;
- значения принимаются, только если есть в перечне позиции справочника, единицы — только из ОКЕИ; проверяет код;
- API без состояния, кроме сессии сужения в Redis по `session_id`; горизонтально масштабируется.

| Метод | Вход | Выход |
|---|---|---|
| `POST /api/v1/autofill` | `name`, `description` | `session_id`; `ktru`: кандидаты (код, наименование, оценка, причина), `remaining`, `final_code`, `question`; `characteristics[]`: имя, значение, единица, `source` (начало, конец, текст), `normalized_from`, `status`; `issues[]`; `degraded[]` |
| `POST /api/v1/autofill/{session_id}/answer` | `characteristic`, `value` | то же состояние `ktru` после сужения; при тупике — `steps[]` (что дополнить или исправить) |
| `POST /api/v1/check` | карточка: `name`, `description`, `characteristics[]` (имя, значение, единица), `ktru_code?` | `issues[]`: `field`, `kind` (`typo` / `mismatch` / `not_in_list` / `moderation_rule`), `message`, `why`, `rule`, `fix?` |
| `GET /api/v1/ktru/{code}` | — | позиция: наименование, характеристики, допустимые значения и диапазоны, единицы, обязательность |
| `POST /api/v1/batch` | файл xlsx или csv | `job_id` |
| `GET /api/v1/batch/{job_id}` | — | прогресс; по каждой строке код КТРУ, число заполненных характеристик, замечания, статус или причина сбоя |
| `GET /api/v1/batch/{job_id}/result.xlsx` | — | файл с исправлениями |
| `GET /api/v1/metrics` | — | результат последнего прогона оценки: метрика, значение, размер выборки, способ расчёта, дата |

Контракт описан в OpenAPI (`/api/docs`, `/api/openapi.json`), pydantic-модели — единственный источник формы ответа.

Демо-стенд портала, не часть модуля (`/api/demo`): очередь заявок, которую на настоящем портале ведёт сам портал.

| Метод | Что |
|---|---|
| `POST /api/demo/submissions` | поставщик отправил заявку (карточка + принятые предложения) |
| `GET /api/demo/submissions` | очередь модератора |
| `GET /api/demo/submissions/{id}` | заявка с результатом `/check` |
| `POST /api/demo/submissions/{id}/decision` | `accept` или `return` с текстом замечаний |

Служебные `/api/health`, `/api/health/ready` остаются для docker и эксплуатации, в интерфейсе их нет.

## 4. Что внутри

Путь `/autofill`:

1. Подготовка текста: аббревиатуры (`Glossary.expand`), опечатки к ближайшему слову справочника.
2. Кандидаты КТРУ: гибридный поиск BM25 + эмбеддинги (pgvector), слияние RRF.
3. Извлечение: сначала правила (числа, единицы, диапазоны, пересчёт г/кг, мл/л), LLM со схемой ответа — только для
   характеристик, которые правила не взяли.
4. Валидация кодом: значение из перечня позиции, единица из ОКЕИ, точечное число — в допустимую корзину
   («80 г/м²» → «≥80 … <90»).
5. Сужение: кандидаты, с которыми расходятся извлечённые значения, отбрасываются; следующий вопрос — характеристика с
   наибольшим приростом информации (больше всего отсекает в среднем), у вариантов — сколько кодов отсекут.
6. Детектор ошибок: опечатки, несоответствия (единица не того типа, противоречие наименованию), значения не из
   перечня, правила модерации портала (не меньше 4 характеристик, единица в отдельном поле, значение не повторяет
   наименование, в наименовании нет значения с единицей).

Сбои — громко и по месту:

- LLM недоступна → только правила, `degraded: ["llm"]`, в блоке «Характеристики» строка «часть характеристик не
  извлечена автоматически»;
- нет эмбеддингов → только BM25, `degraded: ["embeddings"]`;
- ответ LLM не прошёл схему или значения нет в справочнике → один повтор, затем значение отбрасывается; поле пустое
  с пометкой «не найдено в описании», ничего не придумываем;
- пакет: сбой строки не роняет задачу, у строки свой статус и причина;
- кэш вызовов LLM и эмбеддингов в Redis по хэшу входа.

Хранение: сессия сужения и состояние пакета — Redis; справочник — в памяти процесса из файлов `CATALOG_PATHS`
(читается на каждом запросе, меняется раз в загрузку); эмбеддинги позиций и заявки (`submission`) — Postgres;
метрики — JSON последнего прогона `app.tools.evaluate`.

## 5. Справочник до хакатона

Настоящего справочника КТРУ с допустимыми значениями у нас нет: выгрузка портала (`data/portal/`) сохранила только
значения характеристик, без перечней. Справочник организаторов придёт 09.10 в неизвестном формате.

Решение: модуль работает с абстракцией справочника (позиция: код, наименование, ОКПД2, единица, характеристики с
видом, перечнем или диапазоном, единицей, обязательностью) и загрузчиками в неё. Источники по порядку:

1. Тестовый — `backend/tests/fixtures/fake/ktru.json` и `ktru_characteristics.csv` (уже есть, синтетика).
2. Демо — реальные перечни с портала: `GetSku` отдаёт у характеристик `ktruValues` и `spgzValues` (видно в
   `docs/research/sku-47453345.json`), наш `fetch_details.py` их отбросил. Дотянуть по карточкам демо-категорий
   (бумага, канцелярия и ещё 3–5 областей), собрать позиции по СПГЗ/КТРУ. Последовательно, пауза 0,8 с, как раньше.
3. На хакатоне — справочник организаторов через `app.tools.recon` и новый читатель в `app/ingest/readers.py`.

Если пункт 2 не даст перечней (пусто или закрыто), демо идёт на расширенной синтетике с пометкой «демо-справочник»
на странице метрик; это решение фиксируется в отчёте.

## 6. Экраны (образец экрана для портала)

Шапка: слева «Автозаполнение характеристик СТЕ»; навигация по ролям: «Поставщик: Создание СТЕ · Массовая
загрузка», «Модератор: Заявки»; справа «Метрики · API». Без бренда и без индикатора состояния. Витрина компонентов
`/ui` — вне навигации, по прямой ссылке. Страница `/status` и `StatusIndicator` удаляются.

1. `/` — Создание СТЕ. Поля «Наименование», «Описание», кнопка «Заполнить по описанию». Блок «Категория КТРУ»:
   осталось N кодов, вопрос с вариантами и числом отсекаемых кодов, итоговый код. Блок «Характеристики»: значение,
   единица, фрагмент описания (маркер в тексте описания, исправленное — красным карандашом), действия «Принять»,
   «Изменить», «Убрать»; замечание у поля с причиной и исправлением. Внизу «Проверить перед отправкой» (`/check`) и
   «Отправить на модерацию» (`/api/demo/submissions`). Над формой примеры для показа: чистый товар, с опечаткой,
   с неоднозначным КТРУ, с недопустимым значением.
2. `/batch` — Массовая загрузка: файл, прогресс, таблица строк (код, заполнено, замечания), открыть строку в форме,
   скачать файл с исправлениями.
3. `/moderation` — Заявки: очередь слева, заявка в режиме вычитки справа, замечания со ссылкой на правило,
   «Принять» и «Вернуть с замечаниями» (текст возврата собран из замечаний).
4. `/metrics` — для жюри: метрики с размером выборки и способом расчёта.
5. `/developers` — API: схема потока «форма портала → API → предложения → решение человека → поля портала», методы
   с примерами запроса и ответа, ссылки на `/api/docs` и BPMN.

Источник — готовый прототип (`frontend/prototype/`): «Проверка карточки» перекладывается в форму СТЕ, «Пакетная
загрузка», «Модерация», «Качество» переезжают, «Как это работает» становится страницей для разработчиков. Визуальный
язык — `DESIGN.md` (корректура). Маршруты — через `history` (`router.ts`), nginx отдаёт `index.html` на любой путь.

## 7. Проверка

- Бэкенд: pytest на каждый метод контракта (сначала тест), на загрузчики справочника, сужение, детектор, пакет;
  `ruff check`.
- Скрипт оценки `app.tools.evaluate`: золотой набор (обычные, с опечатками, вне справочника, с испорченными
  значениями), Accuracy@1/@5 кода, precision/recall заполнения, precision/recall/F1 детектора, p95 задержки.
- Фронт: `npm run build`, `npm run lint`, e2e playwright по пяти экранам и четырём сценариям, скриншоты 390×844,
  1366×768, 1440×720 с просмотром, скан доступности.
- Сборка целиком: `docker compose up -d --build`, сценарии на 8080.
- BPMN 2.0 с дорожками «Поставщик», «Модуль», «Модератор» в `docs/bpmn/`, PNG рядом.

## 8. Риски

- **П. 7.5 Положения** (проект создаётся на хакатоне, у топ-5 код-ревью и видна история). Доменный код теперь в
  отслеживаемых путях; ничего не коммитится без команды пользователя, решение о коммитах — за ним.
- Справочник организаторов может не совпасть с нашей абстракцией: загрузчик — отдельный слой, остальное его не знает.
- Эмбеддингов в Ollama Cloud нет: без локального Ollama поиск идёт по BM25 (`degraded`).
