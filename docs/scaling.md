# Масштабирование: как устроено и сколько держит

Замеры 04.10.2026, скрипт `backend/app/tools/load_test.py` против поднятого `docker compose`. Сырые итоги
прогонов (JSON-строки) в репозиторий не кладутся: в них имена файлов с данными.

> **Модель с 11.10.2026 — локальная.** Замеры 04–10.10 сняты с Ollama Cloud и локальным Ollama. В решении на
> сдачу чат — `gemma-4-31b-it-Q8_0.gguf` и эмбеддинги — `bge-m3-Q8_0.gguf` в двух экземплярах llama.cpp server
> (`docker compose --profile llm up -d`); задержки и пропускную способность с ними не пересчитывали, цифры ниже
> про бесплатный облачный тариф к ним не относятся. Что остаётся верным: порции пакета, воркеры, Redis, HNSW,
> работа без модели.

## Как масштабируется

```
браузер ─► nginx (web) ─► API (FastAPI, без состояния) ──► Redis: сессии вопросов, пакеты, кэш LLM
                              │  POST /batch: разбор файла,
                              │  строки → Redis, порции по 20 строк → RabbitMQ jobs.batch
                              ▼
                         RabbitMQ ─► worker × N (WORKER_REPLICAS, --scale worker=N)
                                       │  порция: строки из Redis, WORKER_CONCURRENCY строк одновременно,
                                       │  результат строки — Lua в Redis (HSETNX + HINCRBY)
                                       ├─► Postgres + pgvector: HNSW по векторам справочника
                                       ├─► эмбеддинги (llama.cpp server `embed`, bge-m3.gguf, локально)
                                       └─► LLM (llama.cpp server `llm`, gemma-4-31b-it-Q8_0.gguf, локально),
                                           LLM_MAX_CONCURRENCY на процесс
```

- **API без состояния.** Сессия уточняющих вопросов, пакеты и кэш ответов модели лежат в Redis, поэтому
  API можно поднять в нескольких процессах или репликах за nginx. Несколько реплик API мы не замеряли.
- **Пакет делится на порции.** API разбирает файл, кладёт строки в Redis списком в исходном порядке и
  публикует в `jobs.batch` порции по `BATCH_CHUNK_ROWS` строк (по умолчанию 20). Каждая реплика воркера
  держит у себя не больше `ceil(WORKER_CONCURRENCY / BATCH_CHUNK_ROWS) + 1` порций (prefetch), остальные
  ждут в очереди: освободившийся воркер заберёт следующую. На 600 строках три воркера получили порции
  10/10/10, на 2000 строках — 34/34/32 (по логу воркеров).
- **Почему порции, а не строка на сообщение.** Сто тысяч строк дали бы сто тысяч публикаций прямо в запросе
  загрузки и столько же подтверждений. Строка без LLM обрабатывается за 2–7 мс, и накладные расходы
  брокера были бы сравнимы с самой работой. Порции по 20 строк — это 5000 сообщений на 100 тыс. строк
  (публикуются пачками по 200, параллельно). При этом файл в 1000 строк всё равно делится на 50 порций,
  и их хватает, чтобы занять три воркера. Повторная обработка считается по строкам, а не по порциям,
  поэтому размер порции на корректность не влияет.
- **Повторная доставка ничего не считает дважды.** Результат строки пишет один Lua-скрипт: `HSETNX` по
  номеру строки, `HINCRBY` счётчика статуса только при первой записи, `HLEN` как число обработанных строк.
  Если воркер упал посреди порции, RabbitMQ отдаёт её другому воркеру (`NACK_ON_ERROR`), и тот пропускает
  строки, которые уже записаны. Статус пакета (`queued`, `running`, `done`) не хранится, а выводится при
  чтении из счётчиков, так что воркерам не нужно наперегонки его переключать. Сбой одной строки даёт
  этой строке статус `failed`, а пакет продолжается.
- **Порядок в итоговом xlsx — исходный.** Файл собирается из списка строк в Redis кусками по 1000 строк
  (`result_file`), а не в порядке обработки.
- **Поллинг большого пакета дешёвый.** `GET /api/v1/batch/{id}?limit=0` отдаёт только счётчики
  (`processed`, `counts`). Страница пакета у файлов больше 2000 строк опрашивает именно так, а в конце
  показывает первые 1000 строк. Все строки есть в файле с результатом.
- **LLM под лимитами сервера.** У 429 свой бюджет повторов (`LLM_RATE_LIMIT_RETRIES=6`). Пауза берётся из
  `Retry-After`, а без него растёт как 1, 2, 4 … 30 с. Если бюджет исчерпан, строка идёт только по
  правилам и получает `degraded: ["llm"]`, но не падает. Одновременных запросов к модели не больше
  `LLM_MAX_CONCURRENCY` на процесс: ждущий 429 держит своё место, поэтому процесс притормаживает целиком.
  Всего к модели уходит до (1 + `WORKER_REPLICAS`) × `LLM_MAX_CONCURRENCY` запросов одновременно.
- **Векторный поиск — HNSW.** Колонка `vec` без размерности, потому что векторы разных моделей лежат в
  одной таблице. Поэтому индекс построен по выражению `vec::vector(1024)` с условием
  `vector_dims(vec) = 1024` (`vector_cosine_ops`, миграция `d4e5f6a7b8c9`). Запрос в
  `app/search/vectors.py` пишет то же выражение, и `EXPLAIN` показывает `Index Scan using
  catalog_embedding_vec_hnsw_1024`. Фильтр по модели и версии справочника HNSW применяет после обхода
  графа, поэтому включён `hnsw.iterative_scan = strict_order` (pgvector 0.8.6): он добирает k строк.

Как запустить:

```bash
docker compose up -d --build                    # воркеров WORKER_REPLICAS (по умолчанию 2)
docker compose up -d --scale worker=4           # на ходу, без пересборки
```

## Условия замеров

- ПК: AMD Ryzen 7 9700X (8 ядер / 16 потоков), 31 ГБ ОЗУ, Windows 11 + Docker Desktop (WSL2).
- LLM (на момент замера): Ollama Cloud, `gpt-oss:120b`, `LLM_THINK=low`, бесплатный тариф; кэш ответов выключен
  (`LLM_CACHE_TTL_S=0`). Эмбеддинги: `bge-m3` в локальном Ollama на RTX 4080.
- Справочник для пакетов: `data/catalog/testset.json` (128 позиций с портала). Вход: первые N строк
  листа «Все» из `data/testset/testset.xlsx` (публичные карточки портала).
- Большой файл: первые 100 тыс. строк пермской выгрузки СТЕ. Этот прогон шёл без LLM и без эмбеддингов
  (`LLM_BASE_URL` и `EMBED_BASE_URL` указывали на закрытый порт), так что данные организаторов не покидали
  машину.
- Настройки: `BATCH_CHUNK_ROWS=20`, `WORKER_CONCURRENCY=4`, `LLM_MAX_CONCURRENCY=4`, API в одном процессе
  uvicorn.
- «Без LLM» означает, что модель недоступна мгновенно (`LLM_MAX_RETRIES=0`) и характеристики заполняются
  только правилами. «Только BM25» означает, что и эмбеддинги недоступны.
- «До» — код до этих изменений: весь файл одним сообщением, один воркер, строки по одной, после каждой
  строки JSON всего состояния пакета перезаписывался в Redis целиком.
- Время пакета считается от отправки файла до `done`, опрос раз в 0,5 с. «Строк/с» — после загрузки.

² Замер сделан на промежуточной версии записи результата: `HSET` в транзакции вместо Lua-скрипта, разница

мы не гоняли с тремя воркерами: один файл он параллелить не умел.

Распределение статусов строк в прогонах «после» с 1 и с 3 воркерами совпадает: параллельность результат не
меняет.

## Большой файл: память и время

| Что | До | После |

Почему «до» тяжело: строки жили объектами pydantic (~9 КБ на строку пермской выгрузки, со всеми колонками
для итогового файла), а результат собирался из всех строк сразу. Теперь строки при разборе сразу
сериализуются в JSON (~1,4 КБ на строку, `parse_upload_json`), уходят в Redis кусками по 1000, а xlsx
пишется потоково (`write_only`) кусками.

|---:|---:|---:|---:|

### Предел одного файла: 100 тыс. строк и 64 МБ

- Загрузка 100 тыс. строк занимает ~23 с. Вся выгрузка заняла бы ~60 с разбора плюс запись в Redis, а это
  почти половина `proxy_read_timeout 120s` у nginx и минута, пока пользователь видит «Загружаем…».
- Redis держит пакет до `JOB_TTL_S` после последней записи: 100 тыс. строк — ~320 МБ, вся выгрузка —
  ~800 МБ. Два-три одновременных больших пакета ещё помещаются, а 244 тыс. строк каждый — уже нет без
  настройки `maxmemory`.
- С LLM узкое место совсем не в файле. На бесплатном облаке пакет идёт со скоростью ~1,2 строки/с, то есть
  100 тыс. строк обработаются примерно за сутки. Предел файла здесь ничего не меняет.

Пермскую выгрузку (244 тыс.) грузить тремя файлами по ≤100 тыс. строк. Их можно отправить сразу:
порции всех трёх пакетов встанут в одну очередь, и воркеры будут разбирать их вперемешку.

## HNSW: полнота и задержка

Синтетика из кластеризованных векторов 1024 (200 центров + шум, нормированы), косинус, k = 20, 50 запросов,
те же выражение и условие, что в рабочем запросе. Параметры индекса m = 16, ef_construction = 64.

| Векторов | Полный перебор, p50 | HNSW, p50 | recall@20 | Сборка индекса |
|---:|---:|---:|---:|---:|
| 10 000 | 27 мс | 1,1 мс | 1,000 | 2 с |
| 50 000 | 152 мс | 1,4 мс | 0,995 | 40 с |

В демо-справочнике всего 17 векторов, в `testset.json` 128. На таких размерах планировщик сам выбирает

там перебор стоил бы 0,1–0,2 с на каждую строку пакета.

### Бюджет шага 7 с (08.10)

Модель теперь спрашивают только о позиции с определённым кодом и ждут не дольше `LLM_BUDGET_S` (4 с), поэтому
шаг мастера с моделью укладывается в бюджет и при медленном облаке; на 429 «usage limit» — без повторов (было
шесть пауз, 63 с на запрос), после отказа сервиса — пауза модели 2 мин. Без LLM на отложенной выборке
(2 000 СТЕ, `evaluate_holdout`: один процесс, четыре случая одновременно):

| | До 08.10 | После |
|---|---|---|
| `/autofill`: медиана / 95-й перцентиль | 215 мс / 2,7 с | 108 мс / 237 мс |
| Худший случай | 194 с | 1,6 с |
| Дольше 7 с | 1,65 % (33 СТЕ) | 0 % |
| `/answer` (ответ на вопрос категории): медиана / 95-й | — | 22 / 73 мс |

Причины хвоста нашёл профилировщик: опечатку искал полный Левенштейн по перечням из длинных текстов
(«Молочная смесь Малютка» — 1,25 млрд вызовов `min`), а сужение 12 кандидатов сворачивало имена
характеристик 7 млн раз. Теперь расстояние считается не дальше двух правок, имена позиции — словарём,
`fold` запоминает короткие строки.

Память: каждый процесс api и worker держит ≈ 1,9 ГБ (`docker stats`: 1,91 / 1,90 / 1,90 ГБ) против
≈ 0,7 ГБ на справочнике из 2 тыс. категорий — справочник и индекс похожих СТЕ загружаются в каждый процесс.
Горизонтальный рост поэтому упирается в память: на 16 ГБ — до 6–7 процессов. Дальше — один общий индекс
похожих СТЕ вне процессов (Postgres или отдельный сервис поиска) и справочник по требованию.

Двойники («такая СТЕ уже есть», `TWINS_PATH`) и подсказки похожих СТЕ в память процесса не грузятся: это sqlite
на диске только для чтения (`twins.sqlite` 4,1 ГБ на 3,7 млн СТЕ, `exemplars.values.sqlite` 585 МБ), страницы
держит кэш ОС, общий для всех процессов. Поиск двойников по наименованию и модели — 0,8 мс медиана, 2,2 мс 95-й
перцентиль, 8,7 мс худший на 200 новых наименованиях (08.10). С двойниками и векторным поиском на отложенной
выборке медиана `/autofill` — 417 мс, 95-й перцентиль — 805 мс: прибавка — запрос эмбеддинга, а не двойники
(без векторов — 124 / 273 мс).

## Узкие места и что дальше

1. **LLM под лимитом.** С 11.10 предел задают GPU и число слотов сервера (`LLM_PARALLEL`), облачных квот нет;
   цифры ниже — облачный замер. Бесплатный ключ Ollama Cloud кончился 08.10 на ~8,4 тыс. запросов за 2 ч (лимиты на
   5 часов и на неделю): массовые прогоны — с бюджетом запросов. Бесплатный Ollama Cloud выдаёт ~0,8 вызова в
   секунду на ключ при любой параллельности (оценка: модель нужна 72 % строк, столько получили `degraded «llm»` в прогоне
   без неё; это ~216 вызовов на 300 строк за ~260 с). Один воркер с 4 запросами справляется за то же время, что три воркера с 12 и с 81
   ответом 429. Что дальше: свой GPU-сервер (vLLM с continuous batching держит десятки запросов
   одновременно), под него поднять `LLM_MAX_CONCURRENCY`. Если реплик станет много, нужен общий лимит
   через Redis (token bucket), а не лимит на процесс.
2. **Эмбеддинги.** На каждую строку уходит один HTTP-запрос к серверу эмбеддингов (замер — Ollama). Три воркера дают только ×1,6
   (47 → 74 строки/с), потому что упираемся в сервер эмбеддингов. Что дальше: эмбеддинги порции одним
   запросом (`/v1/embeddings` принимает список, 20 текстов за раз), больше слотов у сервера эмбеддингов
   или второй экземпляр.
3. **CPU (правила, BM25, проверки)** масштабируется репликами почти линейно: ×2,8 на трёх воркерах.
   `WORKER_CONCURRENCY` здесь не помогает, потому что один процесс Python исполняет одну сопрограмму
   (GIL); он помогает только перекрыть ожидание эмбеддингов и LLM. Потолок — ядра машины.
4. **API** — `API_WORKERS` процессов uvicorn (по умолчанию 1, `--workers` в `backend/Dockerfile`), состояния
   в нём нет. Замер 10.10, `/autofill` без модели с векторами, 200 запросов из тестового набора, каждый процесс
   ≈ 2,4 ГБ:

   | Процессов API | 1 клиент: медиана / 95-й | 8 клиентов: запросов/с | 32 клиента: запросов/с, медиана |
   |---|---|---|---|
   | 1 (до правки BM25) | 280 / 557 мс | 5,0 | 5,0, 5,6 с |
   | 1 | 237 / 458 мс | 6,7 | 6,9, 4,3 с |
   | 2 | 244 / 449 мс | 7,5 | 9,4, 3,0 с |

   Внутри процесса шаг без сети стал вдвое быстрее (медиана 164 → 86 мс: BM25 по спискам вхождений, кэш
   сравнения слов), а второй процесс даёт ×1,4, не ×2: больше половины времени шага — запрос эмбеддинга к
   одному серверу эмбеддингов (п. 2; замер на Ollama). Что дальше — больше слотов у сервера эмбеддингов или
   второй экземпляр.
5. **Подсказки похожих СТЕ** читают характеристики 10 соседей из sqlite (`exemplars.values.sqlite`,
   585 МБ на 633 тыс. СТЕ) — миллисекунды на запрос, в памяти процессов их нет.
6. **NaN от bge-m3.** На 8 из 2000 текстов (0,4 %) Ollama (замер 08.10) отвечал 500 «unsupported value: NaN». Раньше
   повтор тратил 1,5 с, а потом эмбеддинги выключались на 60 с для всего процесса, и сотни следующих строк
   пакета искались только по BM25. Теперь такой ответ — `LLMInputError` без повторов: только эта строка
   идёт по BM25, остальные с векторами (`degraded_embeddings` = 8 из 2000 при 1 и при 3 воркерах).
7. **Строки с текстом длиннее лимитов `AutofillIn`** получают статус `failed` и текст ошибки. В пермских
   100 тыс. строк такая одна, пакет её пропускает и идёт дальше.

## Как повторить

```bash
cd backend
# подмножество тестового набора (в scratch, не в репозиторий)
uv run python -m app.tools.load_test subset ../data/testset/testset.xlsx --rows 2000 --dst /tmp/ts2000.xlsx
uv run python -m app.tools.load_test batch /tmp/ts2000.xlsx --label "3 воркера"
uv run python -m app.tools.load_test check /tmp/ts2000.xlsx --concurrency 1,8,32 --requests 500
uv run python -m app.tools.load_test autofill /tmp/ts2000.xlsx --concurrency 1,8,32 --requests 300
uv run python -m app.tools.load_test parse /tmp/ts2000.xlsx      # разбор и пик памяти в этом процессе
```

Число воркеров нужно сверять по логу (`docker compose logs worker | grep "пакет <id>"`, строки «воркер
<host>»), а не по команде. Без LLM: в override-файле compose задать `LLM_BASE_URL` на закрытый порт и
`LLM_MAX_RETRIES=0`. Данные организаторов гонять только так.
