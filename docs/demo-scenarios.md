# Сценарии мастера создания нового товара

Область: поток C, пункты C1–C14 из `final_plan.md`. Поставщик описывает свой товар;
КТРУ задаёт структуру и допустимые значения, но не заменяет введённые свойства.
Фото необязательно. Новые характеристики подтверждает модератор.

## Запуск проверок

После завершения всех этапов реализации:

```powershell
cd frontend
npm test
npm run lint
npm run build
playwright-cli open http://localhost:8080/
playwright-cli --raw run-code --filename=e2e/wizard.js
playwright-cli --raw run-code --filename=e2e/flows.js
```

Адрес берётся из открытой страницы: можно использовать отдельный локальный стенд.
`wizard.js` проверяет интерфейс на фиксированных контрактных ответах API и перехватывает
отправку тестовой заявки. Успех этого сценария не подтверждает качество извлечения сервера.
`flows.js` использует настоящий API и текущий справочник, без подмены ответа. Все провалы
вызывают ошибку; отсутствие ожидаемого значения не считается допустимым запасным исходом.
Исходные старые сценарии сохранены в `*.legacy.js`, старые инструкции — в
`demo-scenarios-legacy.md`. Они относятся к прежним данным и правилам, не являются текущей приёмкой.

## Сценарий демонстрации

1. Открыть «Создание СТЕ». Вставить название и описание своего товара.
2. На вопросе о типе прочитать название, ОКПД2, число позиций, совпадения, пропуски и противоречия.
   Пустые причины не выдумываются. При недоступном справочнике сведения явно не загружены.
3. Выбрать тип. По истории сужения проследить путь до конкретного кода КТРУ.
4. Проверить «Общие сведения», «Характеристики КТРУ», «Характеристики портала» и «Новые характеристики».
   Раздел без характеристик не показывается. Обязательные поля КТРУ идут первыми.
5. У перечня выбрать допустимое значение; у диапазона ввести точное число. Например, 500 мм,
   а не «400–800». Нельзя принимать подсказку другого товара без проверки своего описания.
6. Открыть проверку. Сводка показывает обязательные заполненные поля, число отклонений КТРУ
   и новых характеристик. Заполненность не является подтверждением соответствия.
7. Прочитать происхождение КПГЗ: связь с КТРУ, поиск без подтверждённой связи или отсутствие связи.
8. Отправить без фото. Пустое обязательное поле должно вернуть к заполнению. Сбой `/check`
   должен отключить отправку и дать повторить проверку.

## Ожидания до прогона

| Случай | Ожидаемое поведение |
|---|---|
| Пустой текст, пробелы и переносы строк | Заполнение не начинается |
| Описание с HTML, кавычками, Unicode | Показывается текстом, код не исполняется |
| «Дрель ручная электрическая», 800 Вт, патрон 13 мм | Среди кандидатов есть тип дрели; свойства не выдумываются |
| «Тумба офисная деревянная», «Вид материала корпуса: глина» | «Глина» сохраняется и получает объяснение несоответствия, не заменяется деревом |
| «Куртка зимняя мужская», ткань полиэстер, размер 52 | Тип куртки; размер остаётся свойством товара |
| Пустая обязательная высота | Не засчитывается, отправка возвращает к полю |
| Диапазон в ответе на вопрос | Это выбор позиции; в поле требуется конкретное число |
| Ручная правка значения вне КТРУ на допустимое | Старое несоответствие не переносится на новое значение; запускается проверка |
| Новое свойство | Отдельный раздел и счётчик, требуется подтверждение модератора |
| Изменение типа или ответа | Прежние ответы очищаются, совместимые ручные правки сохраняются |
| Ошибка или задержка `/check` | Нет «вне КТРУ 0» вместо неизвестного результата, отправка недоступна |
| Отсутствие фото | Допускается отправка при заполненных обязательных полях |
| 390×844 и 1366×768 | Подписи над полями, сводка и объяснения читаются без горизонтальной прокрутки |

Известный до этого этапа дефект потока B: сервер может терять «Вид материала корпуса: глина».
Живой сценарий обязан сообщить о провале, если дефект воспроизводится. Контрактный UI-сценарий
с «глиной» не закрывает этот дефект. Фактические результаты прогонов фиксируются отдельно;
таблица выше описывает требования, а не заявляет об успешном выполнении.
