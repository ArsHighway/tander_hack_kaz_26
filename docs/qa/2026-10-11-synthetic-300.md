# Синтетический набор 300 описаний: как модуль считывает данные (11.10.2026)

> Срез на дату документа. С 11.10.2026 модель — локальная `gemma-4-31b-it-Q8_0.gguf` в llama.cpp server, Ollama и облачные ключи в решении не используются ([model-choice.md](../model-choice.md)); упоминания Ollama, облачных квот и `gemma4:31b` ниже описывают состояние на тот день.

Набор команды «НАБОРЫ ОПИСАНИЙ» — 100 описаний инструментов, 100 мебели, 100 одежды: чистые, с опечатками, одной
строкой, разговорные («болгарка ушм 125 диск мощность девятьсот ватт…»), с абсурдом («Страна: Ваканда», «Мощность:
-1510 Вт»). Каждое прошло весь конвейер с моделью gemma4:31b в двух вариантах, каждый результат просмотрен глазами
(LLM, 12 ревьюеров по 25 товаров). Разбор каждого товара — [2026-10-11-synthetic-300-items.md](2026-10-11-synthetic-300-items.md),
сырые данные — `data/qa/2026-10-11-synth-300/` (вне git).

## Итог

- **Лимит 1 минута держится с запасом.** Самое долгое описание — 13 с как на стенде и 31 с с правкой текста моделью;
  больше 60 с — ни одного.
- **Тип находится почти всегда, но верен у 57 %.** Тип найден у 296 из 300; ревьюеры считают его верным у 170, верным,
  но с не той позицией КТРУ — у 76, неверным — у 50.
- **Карточку целиком ревьюер принял у 14 из 300** (good), частично — у 155, плохо — у 131.
- **Главная поломка — бюджет модели 4 с.** Под нагрузкой 104 из 368 вызовов модели (28 %) не уложились в 4 с, и 79
  описаний из 300 остались без дозаполнения моделью. При бюджете 20 с сорвались 2 вызова из 598.
- **Правка текста моделью почти ничего не даёт.** Ревьюеры: лучше — 42, хуже — 20, без разницы или спорно — 238. Текст она
  меняет у 91 описания из 300, а стоит 2–3 с на каждое.
- **Ключи не кончились.** Три ключа по кругу, около 970 вызовов, ни одного «usage limit».

## Как запускали

```
cd backend && set -a && . ../.env && set +a
uv run python -m app.tools.run_descriptions "НАБОРЫ ОПИСАНИЙ - Лист1.csv" --out ../data/qa/2026-10-11-synth-300 --concurrency 10
```

`app/tools/run_descriptions.py` собирает конвейер как на стенде: справочник типов КТРУ, похожие СТЕ с векторами,
двойники, КТРУ XML, pgvector из compose. Сессии хранятся в памяти, кэша ответов модели нет. Ячейка CSV — одна вставка
в мастер: первая строка — наименование, остальное — описание.

- **`base`** — как сейчас на стенде: модель дозаполняет поля определённой позиции не дольше `LLM_BUDGET_S` = 4 с.
- **`norm`** — сначала модель исправляет опечатки и сокращения во всём тексте (промпт `NORM_SYSTEM` из
  `llm_chaos`, правку проверяет `accept_fix`), потом тот же конвейер с бюджетом 20 с.

На вопрос мастера (тип, позиция КТРУ, характеристика) прогон отвечает первым настоящим вариантом, как поставщик,
который соглашается с первым предложением. **Поэтому значения с `[answer]` выбрал прогон, а не модуль.** Ревьюеры
часто писали их в «выдумано», но настоящий дефект здесь другой: вопрос задан, хотя ответ есть в тексте, или первым
вариантом стоит неверный (раздел 2, п. 3).

## 2. Проблемы, по убыванию вреда

Число — товары, где ревьюер это отметил (поиск по его записям; один товар может попасть в несколько строк). Помеченное
«✔» я проверил сам по выводу прогона.

### Модель: время и промпт

1. **✔ Бюджет 4 с режет модель в 28 % вызовов.** У перфоратора ИНС-001 модель не успела, и «Мощьность: 780 Вт»,
   «частота 1100 об/мин» ушли в extra. С бюджетом 20 с то же описание заполнилось. В лимит минуты помещаются и
   правка текста, и дозаполнение. **Поднять `LLM_BUDGET_S` до 15 с.**
2. **✔ Модель пересчитывает единицы вопреки правилу 5 промпта.** «Мощность: 650 МВт» → «Потребляемая мощность = 650
   Вт» [llm] (ИНС-073), хотя правило и `Мощность` поймало block «МВт и Вт отличаются в 10⁶ раз». Нужна проверка кода:
   единица в ответе модели не может быть другой, если в цитате своя.
3. **✔ Модель кладёт весь текст в одно поле**: «Описание = Тип конструкции: прямая. Вид материала корпуса: ЛДСП. …»
   (МЕБ-012). Нужна проверка кода: значение не длиннее N слов, если у поля нет перечня.
4. **Одно значение — в нескольких полях** (72 товара): «латексные» в 6–7 полях (ОДЕ-086), «резиновые» в 6 полях,
   «Масса молотка = 0,7 кг» и «Вес = 700 г» (ИНС-002). Частью это правила, частью модель дозаполняет одноимённое
   поле портала. Промпт: «одна цитата — одно поле»; код: не брать модельный элемент, если его цитата уже лежит в другом
   поле.
5. **Подсказки похожих СТЕ спорят с текстом** (117): «Вес = 0 кг», «Пластик» у сиденья при «велюр» (МЕБ-032), «Бук» при
   «сосна» (МЕБ-077). Подсказку не показывать, если текст называет другое значение этого поля или его материал.

### Правила извлечения (код, не промпт)

1. **✔ Метка с опечаткой не ложится в поле**, хотя детектор опечаток её видит: «Мощьность: 780 Вт» → extra
   «Мощьность=780» и info «Похоже на опечатку: «Мощьность» — «Мощность»» (ИНС-001). Метку надо сверять с полями после
   того же исправления опечатки, что и наименование.
2. **✔ Слово метки становится значением**: «Длина: 210 мм» → «Тип губок = Длинные» (ИНС-009, ИНС-016); «полки» в
   «поликлиники» → «Наличие полок = Да» (МЕБ-047).
3. **✔ Ответ есть в тексте, а вопрос задаётся, и первым вариантом стоит неверный**: «Тип питания: встроенный
   аккумулятор» → вопрос «Тип питания», варианты «От сети», «От аккумуляторных батарей» (ИНС-054, ИНС-074, ИНС-084).
   Это и есть «приведение к КТРУ», которое ждёт модель: `match_to_list` написан, но к сужению не подключён (D4 плана).
   Подключить его до вопроса: вариант, который модель выбрала по тексту, — ответ без вопроса, если код его проверил.
4. **✔ Диапазон схлопывается до верхней границы**: «Рост: 170–176 см» → «Рост = 176 см», и дважды (ОДЕ-083; также
   ОДЕ-088, 092, 093). Есть перечень КТРУ — выбрать в нём корзину с этим диапазоном; нет — диапазон или вопрос.
5. **✔ Состав портится**: «100% хлопок» → «Состав = 100 хлопок %» (ОДЕ-057; 37 товаров с составом). Пары
   «волокно — доля» разбирать отдельно, основное сырьё — по большей доле.
6. **✔ Минус теряется**: «Мощность: -1510 Вт» → 1510 Вт без замечания (ИНС-085). То же «минус 85 см», «-28 л» (47
   товаров с минусом или отрицательным числом).
7. **✔ «ПВХ» записывается как «ПВX» с латинской X** (МЕБ-076, МЕБ-084, МЕБ-096; 9 товаров). В тексте кириллица,
   латинская X — в перечне справочника, а `fold` их склеивает. Чинить данные справочника (кириллица в значениях), не
   вывод.
8. **✔ Нелепая единица молча становится правдоподобной**: «500 килотонн» → «Максимальная допустимая нагрузка на полку
   = 500 кг» без замечания (ОДЕ-081), «10 метров» → 10 мм (МЕБ-034), «1.2 километра» → 1,2 мм (ИНС-061). Число
   с другой величиной в поле не брать, а давать warn.
9. **Числа словами и дюймы не читаются** (73): «девятьсот ватт» (ИНС-022), «сорок второй размер» (ОДЕ-035), «полтора
   метра» (МЕБ-061), «7,8 дюйма» (ИНС-016).
10. **Бренд и модель теряются** (35): «Walker Pure Authentic», «SL Born B 201», «КЭ10».

### Проверки и замечания

1. **✔ Ложная опечатка меняет товар**: «сорок» → «сорочка», «Товар подобран по исправленному наименованию» (ОДЕ-035;
   также МЕБ-020, МЕБ-068). Числительные не исправлять.
2. **Ложная опечатка у верного слова**: «Похоже на опечатку: «Женская»» (ОДЕ-060, 070, 090); «Рюкзаг» → «Рюкзаки»
   вместо «Рюкзак» (ОДЕ-065).
3. **Абсурд записан молча** (129): страна «Ваканда» (ОДЕ-081), «Асгард» (ИНС-068), «Седьмое измерение» (ИНС-062);
   «вес 80 тонн» у сейфа даёт только info (МЕБ-037); «шерсть дракона» → «шерсть» (ОДЕ-049). Страну сверять со
   справочником стран; число вне `plausible` поля — warn, а не info.
4. **info «Число X подходит нескольким характеристикам»** (64 товара) — шум: «39» у полуботинок «подходит» к «Вес
   брутто» и «Срок службы» (ОДЕ-060), хотя «Размер обуви: 39» уже в поле.
5. **✔ Обязательное поле КТРУ пусто, когда то же значение легло в поле портала**: «Размер обуви (штихмассовый) = 39»,
   а обязательный «Размер (штихмассовый)» пуст, block (ОДЕ-060, 070). Синонимы полей КТРУ и портала не склеены.
6. **Непонятные тексты замечаний**: warn «В наименовании «4504л».» (ОДЕ-060); block «Ожидается: «1e-07» не число»
   (МЕБ-050).

### Тип товара

1. **Неверный тип у 50 товаров, верный часто вторым или третьим**: «болгарка ушм 125…» → «Материалы и изделия
   шлифовальные», «Шлифмашина» вторая (ИНС-022); «геймерское кресло с подставкой для ног…» → «Подставки для ног
   офисные» (МЕБ-028); «Костюм рабочий мужской» → детский (ОДЕ-088); «Стол рабочий» → «Экраны разделительные» (МЕБ-018).
   Главное слово проигрывает дополнению «с X» и разговорным словам. Есть `rerank_types` за флагом
   `LLM_RERANK_TYPES` (выключен); следующий эксперимент — включить его на этом наборе.
2. **Правка текста иногда уводит тип**: «обувь спец» → «обувь специальная» сдвинула кандидатов к «диэлектрической»
   (ОДЕ-037); «ключом» — к «Шкафы для тубусов и ключей» (МЕБ-033). Тип по `base` и `norm` разошёлся у 9 товаров.

## 3. Правка текста моделью (`norm`): что даёт

- Текст правит у 91 описания из 300. 21 правку код отбросил: числа не сошлись или новое слово не похоже ни на одно
  старое.
- **Помогает** на опечатках в метках и наименовании: «Мощьность», «Расия», «Шырина», «ССтул», «телек» → «телевизор».
  Самый явный случай — МЕБ-099: из «ССтул» тип «Секция стульев» стал «Стул».
- **Вредит**, когда разворачивает то, что правилам нужно коротким:
  - «ПВХ» → «поливинилхлорид» (МЕБ-084, новый block);
  - «об/мин» → «оборотов в минуту» (ИНС-077, 087: значение 200 пропало);
  - «спец» → «специальная» (ОДЕ-037, другой тип).
- **Стоит** 2,4 с в p50 на каждое описание, а 2/3 описаний она не меняет.

**Рекомендация:** звать правку только когда детектор опечаток или раскладки что-то нашёл. Промпт сузить до опечаток
(см. ниже). Тогда время лишь там, где есть что править.

## 4. Предлагаемые правки промптов

`NORM_SYSTEM` (правка текста, `app/tools/llm_chaos.py`; в конвейер пока не встроен):

```
Ты исправляешь опечатки в тексте карточки товара для госзакупок. Исправляй только слова с опечатками
(«Мощьность» → «Мощность», «Расия» → «Россия», «ССтул» → «Стул»). НЕ раскрывай сокращения и аббревиатуры
(ПВХ, ЛДСП, МДФ, об/мин, уд/мин, хб, СИЗ, спец), не переводи единицы, не меняй числа, знаки («-», «±»),
числительные словами («сорок второй»), бренды, модели и артикулы. Ничего не добавляй и не удаляй, порядок
слов и переносы строк сохрани. Если исправлять нечего — верни текст без изменений.
Ответ — JSON {"text": "<исправленный текст>"}.
```

`SYSTEM` дозаполнения (`app/extract/llm_fill.py`), дописать правила:

```
7. Имя характеристики в тексте может быть с опечаткой или другим словом («Мощьность», «Ширина полотна» —
   «Ширина лезвия»): относи значение к характеристике из списка по смыслу метки.
8. Значение может быть сказано другими словами, чем вариант перечня, при том же смысле: «встроенный
   аккумулятор» = «От аккумуляторных батарей», «пассатижи» = «Плоскогубцы комбинированные». Тогда value —
   вариант перечня, quote — слова текста. Если смысл другой — не включай.
9. Каждая цитата — только для одной характеристики. Не раскладывай одно слово («латексные», «дерево») по
   нескольким полям, если текст не говорит о каждом из них.
10. Диапазон («170–176 см», «48–50») — value целиком, как в тексте; не выбирай один край.
11. Состав ткани — каждое волокно с долей отдельно, как в тексте («65% хлопок»).
12. Число с единицей другой величины, чем у характеристики («500 килотонн» у нагрузки, «10 метров» у
    толщины), минус у величины, которая не бывает отрицательной, страну, которой нет, — не включай в items,
    а добавь в "suspicious": [{"name", "quote", "why"}].
```

Правило 12 требует поля `suspicious` в схеме ответа (`LLMItems`) и замечания `warn` в коде. Правило 8 сейчас прямо
противоречит правилу 4 («иное слово… не включай»), поэтому 4-е надо переписать вместе с ним. Остальное — без смены
схемы. Код уже проверяет цитату и значение (`_quote_has_value`), поэтому «девятьсот ватт» → 900 он отбросит. Чтобы
модель помогала с числами словами, проверке нужен разбор числительных.

## 5. Что делать, по «баллы × дешевизна»

1. `LLM_BUDGET_S` = 15 с: одна строка в `.env`. Вернёт модель 79 описаниям из 300.
2. Подключить `match_to_list` к сужению до вопроса (раздел 2, правила, п. 3). Это главное «приведение под КТРУ», и
   код уже написан.
3. Правила: метка с опечаткой, слово метки не значение, диапазон, состав, минус, ПВX в справочнике, «сорок» →
   «сорочка». Каждое — тест на пример из таблицы разбора.
4. Новые правила промпта дозаполнения (п. 7–11), затем `suspicious` (п. 12).
5. Правка текста — только при найденной опечатке, с новым `NORM_SYSTEM`.
6. Замер: этот же набор `run_descriptions` (5 мин) и ревью — до и после каждой правки.
