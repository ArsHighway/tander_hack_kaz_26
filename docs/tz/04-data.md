## КТРУ (XML ЕИС)

- Вложенные архивы `NNN_nsiKTRUNew_all_2026-10-05.zip`; внутри `nsiKTRUNew_all_actual_<дата>_NNN.xml` (82 файла)
  и `nsiKTRUNew_all_not-actual_…xml` (101 файл). По методичке берём только **actual**.
- В actual — 81 465 позиций: статус `ACTIVE` 60 087, `TERMINATED` 21 378; тегов `<oos:characteristic>` 330 548.
- Позиция (`oos:position/oos:data`): `code` (`32.50.13.190-00021`), `versionCode`, `version`, даты включения,
  публикации, изменения, `name`, `OKPD2` (код и имя), `status`, `applicationDateStart`, `OKEIs` (единицы позиции),
  `NSI/classifiers` (связи с классификаторами), характеристики с допустимыми значениями, диапазонами и единицами
  (структура — стр. 133 описания).
- Категории хакатона по ОКПД2 позиций actual: одежда (раздел 14) — 1 198, мебель (31) — 388, инструменты —
  в разделах 25 (1 087) и 28 (2 684) вместе с другим; точный список — по кодам позиций КТРУ из листов «Конечная
  категория ПП» и по ОКПД2.
- **Справочник из XML собран** (`app.catalog.ktru_xml`, `build_ktru_catalog --xml`): 82 файла actual взяты, 101
  not-actual отброшены, 60 087 позиций `ACTIVE`, 234 363 характеристики → `data/catalog/ktru_xml.json` (53 МБ),
  `KTRU_PATHS` смотрит на него. Сверка с разбором карточек ЕИС (`ktru.json`, 32 137 позиций): общих 32 123,
  значения совпали у 99,85 % характеристик, единицы — 99,99 %, обязательность — 99,99 %. Расхождения — в пользу
  XML: пороги «≥ + 10», которые не разобрала страница, и характеристики, которых на странице не было.
- **Привязка категорий хакатона к КТРУ** (617 категорий листа 2): живые ссылки стандартов портала есть у 245
  (40 %), у 183 ссылок нет, но есть позиции КТРУ с тем же ОКПД2, у 152 нет ни того ни другого, 37 категорий нет в
  наших стандартах. Привязку по ОКПД2 проверили и не взяли: коды «прочие» (…190, …299) собирают чужие товары
  («Пилы для обработки дерева» → «Комплект для ремонта велосипеда»), а фильтр по главному слову оставляет 45
  категорий из 183 и всё равно ошибается («Ключи трещоточные» → «Ключ гаечный разводной»). Неверный код хуже,
  чем «в КТРУ нет».

## Примеры выгрузок (xlsx, по два листа)

Разбор — `uv run python -m app.tools.recon "../data/organizers/Казань 2026/Примеры выгрузок"` (из `backend/`).

**Лист1 — СТЕ портала** (Инструменты 99 998 строк, Мебель 99 995, Одежда 99 993):
`ID СТЕ`, `Наименование СТЕ`, `Модель`, `Производитель`, `Страна происхождения`, `Характеристики`.
Категории у строки нет. Характеристики одной строкой через « | » (в 6 000 строках « | » — 63 574 раза, « / » —
13), имя и значение разделены пробелом, без двоеточия: «Масса 10.20000 кг | Тип …». Имя от значения отделяется
только по списку имён характеристик (лист 2, стандарты портала, КТРУ). Много нулевых значений («Вес 0.00000 кг»,
«Высота 0.00000 мм»). **Все СТЕ листа 1 уже есть в нашей выгрузке портала** (`data/ste_full`): по `ID СТЕ`
нашлись 99 949 из 99 998, 99 995 из 99 995 и 99 993 из 99 993, и почти все лежат в категориях листа 2 — значит,
категория у каждой строки известна через нашу выгрузку.

**Лист2 — типовые свойства категорий** (278, 139 и 200 категорий; в наших стандартах есть 255, 138 и 187) (Инструменты 41 352 строки, Мебель 42 395, Одежда 22 905):
`Конечная категория ПП`, `Код КПГЗ`, `Наименование кода КПГЗ`, `Название характеристики`,
`Тип (базовая/эталонная/категореобразующая)`, `Тип характеристики` (Справочник, Признак, Целое числовое значение,
Текст), `Значения характеристики`, `Единица измерения`, `ID / Наименование / Значения связанной эталонной
характеристики СПГЗ` (значения с корзинами «>= 1.00000 ... < 2.00000»). Это тот же стандарт категорий портала, что
у нас в `data/standards/` и `data/catalog/standards.json`, только для трёх категорий.

## Что из этого следует

1. Справочник КТРУ — из XML (actual, `ACTIVE`): «превалирующим является справочник КТРУ». Сделано, см. выше.
2. Лист 2 — шаблон категорий портала (КПГЗ) для первого этапа; лист 1 — живые СТЕ для похожих СТЕ, двойников и
   оценки (наименование → категория по совпадению с нашей выгрузкой портала по `ID СТЕ`).
3. Разбор характеристик листа 1: читатель формата «имя значение / …» по словарю имён.

прогоне (4 запроса параллельно) — p50 0,4 с вместо 0,08 с: вектор запроса считает сервер эмбеддингов (в замере — Ollama).

**Обязательные характеристики КТРУ (10.10.2026).** Стандарты портала помечают обязательными 142 из 211 тыс.
характеристик, в XML КТРУ обязательна половина. Обязательная у итоговой позиции КТРУ теперь обязательна и в
карточке (мастер не даёт отправить пустой, `/check` — `warn`). На отложенной выборке обязательных полей стало 358
вместо 48, модуль заполняет сам 46 % из них; «без единого действия» — 30,0 % вместо 34,9 %: честнее, а не хуже.

**Проверено и не взято (10.10.2026).** Значение перечня, найденное в тексте, правила ставят во все поля, где оно
есть в перечне: «фанера» — и в каркас, и в сиденье, одно «нет» — в 7–9 полей-признаков. Три правки (контекст
соседних слов в описании, в наименовании, метка поля рядом с «да/нет») на отложенной выборке убирали больше верных
значений, чем неверных: точность правил падала с 65,6 % до 64,3–65,3 %. На портале СТЕ заполняют признаки «Нет» по
умолчанию, а материал у частей мебели обычно один — эталон с этим согласен.

**Текст против подсказок и чисел (10.10.2026, аудит 09.10, пп. 5, 8, 14).** Подсказка похожих СТЕ или
двойника не ставится, если текст говорит о поле иное (`app.search.against_text`), а `/check` сверяет число поля с
описанием тем же разбором. Ложные срабатывания меряются даром: описания отложенной выборки собраны из «данных»
полей, «целевых» в тексте нет, и довод против подсказки целевого поля всегда ложный. Первая версия (любое число той
же величины, слово перечня где угодно в тексте) выбросила 52 подсказки похожих и 20 двойников, из них верных 29 и
18; итоговая (число с подписью поля или единственного поля этой величины, явная «Метка: значение» — только полное
имя, без диапазонов, размеров, годов и артикулов) — 3 из 1 725, точность и полнота подсказок не изменились. Число
поля против описания на 44 тыс. честных карточек: замечание у 0,25 % (первая версия — 8,9 %), чаще это настоящие
ошибки («Количество листов: 160» при «80 листов», «Рост: 158» при «рост 152»).

Пределы категории (`app.tools.plausible_ranges`): p1–p99 значений СТЕ категории с запасом есть у 15,6 тыс.
характеристик стенда. Вне пределов значений поставщиков отложенной выборки: запас «½ размаха, ×1,5, ÷2» — 1,9 %,
**«размах, ×2, ÷3» — 1,4 % (взят)**, «×5, ÷5» — 1,0 %; это в основном ошибки единиц («Высота: 6000 мм» у детской
кровати, «Ширина: 0 мм»). Наименования работ и услуг («Ремонт мягкой кровли», «Услуги по уборке») получают «похоже
на работы (услугу), а не на товар» вместо похожих товаров.

**Нетронутая часть выборки (10.10.2026).** Решения подбирались на первых 2 000 случаях перемешанной выборки;
остальные (`evaluate_holdout --skip 2000`) модуль раньше не видел. Категории хакатона, 2 041 нетронутый случай:
категория первой / среди пяти — 78,1 % / 88,5 % (на подобранных 77,5 % / 87,7 %), без вопроса верно — 93,2 %,
уверенные ошибки — 3,6 %, точность того, чего нет в тексте, — 76,2 %: подгонки под выборку не видно. Файлы —
`data/metrics/holdout_kazan_untouched.json`, `holdout_untouched.json`.

**Склейка синонимов характеристик в категориях хакатона — проверено и не взято (10.10.2026).** Пары, которые модель
назвала одной характеристикой, а СТЕ портала не опровергли (`find_synonyms`), без длинных перечней: 2 146 пар,
характеристик в шаблонах на 1,8 тыс. меньше. На отложенной выборке почти без изменений (точность правил 65,7 % →
64,9 %, обязательные заполнены 62,9 % → 64,2 %), но на демо-карточках появились ошибки: у молотка «Материал бойка:
Фиберглас» (склеен с «Материалом корпуса»), у шкафа «Срок службы: 22» из «ШРМ-22» и «Цвет: Металлический», стол
потерял «Вид материала столешницы: ЛДСП». Пары модели слишком грубы для склейки без проверки глазами.

Прогон нашёл падение `/autofill` на единицах, далёких больше чем на 10⁹ («нм» к «км»), — исправлено.
Строки листа 1 как ввод поставщика (наименование + «имя значение | …») модуль разбирает: на 12 случайных строках
категория верная у всех, правилами из текста заполнено 2–44 поля.
