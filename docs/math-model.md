# Математическая модель модуля

Модуль решает три задачи: находит позицию КТРУ по свободному тексту, заполняет характеристики позиции
значениями из текста и объясняет ошибки карточки. Ниже — формулы, пороги и то, как пороги подобраны.
Код — `backend/app/search/`, `extract/`, `values.py`, `narrowing.py`, `checks/`; метрики — `evaluation/`.

## 1. Обозначения

- $P = \{p_1, \dots, p_N\}$ — позиции справочника; у позиции $p$ есть наименование $name(p)$ и характеристики
  $C(p)$. Характеристика $c$ — имя, вид (качественная или количественная), единица $u_c$, перечень
  допустимых значений $V_c$ (значения или корзины «≥80 … <90»), диапазон $[lo_c, hi_c]$, признак обязательности.
- $x$ — вход поставщика: наименование $x_n$ и описание $x_d$.
- Справочник по умолчанию на стенде — категории портала со стандартом (шаблоном характеристик): 8 569
  позиций, перечни значений — из 3,68 млн живых СТЕ (`app.tools.build_standard_catalog`, план и замеры —
  `docs/plans/2026-10-06-standard-catalog.md`). Позиции КТРУ — отдельный справочник из карточек ЕИС
  (32 137 позиций — все, на которые ссылаются стандарты), на них ссылаются характеристики стандарта (раздел 4.1).
- $T(s)$ — токены строки: слова в нижнем регистре, `ё → е`, латинские двойники кириллицы приведены, основа по
  Snowball (слова от 4 букв), стоп-слова убраны.

## 2. Поиск кандидатов

### 2.1. BM25 по позициям

Документ позиции — наименование, имена и значения характеристик. Оценка Okapi BM25 ($k_1 = 1{,}5$, $b = 0{,}75$):

$$
\mathrm{BM25}(q, p) = \sum_{t \in T(q)} \mathrm{idf}(t)\,
\frac{f_{t,p}\,(k_1 + 1)}{f_{t,p} + k_1\left(1 - b + b\,\frac{|p|}{\overline{|p|}}\right)},
\qquad \mathrm{idf}(t) = \ln\!\left(1 + \frac{N - n_t + 0{,}5}{n_t + 0{,}5}\right).
$$

Опечатка запроса: незнакомый токен из букв длиной от 5 заменяется ближайшим словом словаря с той же первой
буквой при расстоянии Левенштейна 1 (от 8 букв — 2); два равных кандидата — не заменяется.

### 2.2. Нормированная оценка и отказ «вне справочника»

Чтобы отказ не зависел от длины запроса, оценка лучшей позиции делится на оценку идеального документа,
совпавшего со всеми словами запроса:

$$
S(q) = \frac{\max_p \mathrm{BM25}(q, p)}{(k_1 + 1)\left(\sum_{t \in T(q) \cap D} \mathrm{idf}(t)
+ w_u \sum_{t \in T(q) \setminus D,\ t \text{ без цифр}} \mathrm{idf}_{\max}\right)},
$$

где $D$ — словарь справочника, $\mathrm{idf}_{\max} = \ln(1 + (N + 0{,}5)/0{,}5)$ — idf слова, которого нет нигде,
$w_u = 0{,}5$: незнакомое слово тянет оценку вниз (товар может быть вне справочника), но не в полную силу —
бренды и модели в справочнике не встречаются никогда. Токены с цифрами (артикулы, «500л») в делитель не входят.

Порог по наименованию $x_n$ решает, идёт ли в слияние список BM25:

$$
\text{открыто} \iff S(x_n) \ge \theta \;\lor\; \Bigl(S(x_n) \ge \tfrac{\theta}{2} \;\land\;
\text{первое слово } x_n \in T(name(p^*))\Bigr), \qquad \theta = 0{,}2 .
$$

Второе условие — для «Отвертка SPARTA 12345 …»: главное слово совпало, а бренд и модель занижают $S$.
Порог $\theta$ подбирается в `app.tools.evaluate` (раздел 6). Отказ «вне справочника» — когда пусты все
списки кандидатов (BM25 после порога, векторы, похожие СТЕ) или больше всего голосов похожих СТЕ у класса
«не товар» (раздел 2.4).

Дополнительно кандидат $p$ отбрасывается, если ни одно слово наименования $x_n$ длиной от 3 букв не входит в
$T(name(p))$ (слово «белый» есть в перечнях многих позиций, но позицию не определяет), и если слово с отрицанием
(«не нитриловые», «без хлора») есть в документе позиции. Кандидат с оценкой ниже половины лучшей не сужается.

### 2.3. Векторный поиск и слияние

Текст позиции и запроса кодируется моделью эмбеддингов (bge-m3, 1024 измерения), близость — косинус по индексу
pgvector. Векторный кандидат принимается при $\cos \ge 0{,}6$. Списки сливаются Reciprocal Rank
Fusion:

$$
\mathrm{RRF}(p) = \sum_{r \in \{\text{BM25}, \text{векторы}\}} \frac{1}{k + \mathrm{rank}_r(p)}, \qquad k = 60 .
$$

RRF не требует сравнимых шкал у двух поисков. Без модели эмбеддингов остаётся BM25, ответ помечается
`degraded: ["embeddings"]`.

### 2.4. Похожие СТЕ портала

Текст позиции (название категории и её характеристики) плохо похож на то, как поставщик называет товар;
похожи наименования уже размеченных СТЕ. Индекс — наименования живых СТЕ с кодом категории (до 300 на
категорию, без отложенной выборки, `app.tools.build_exemplars`). Для наименования $x_n$ берутся 30 ближайших
СТЕ по BM25 $s_1 \ge \dots \ge s_{30}$, и каждая голосует за свою категорию $k(i)$:

$$
\mathrm{share}(k) = \frac{\sum_{i:\,k(i)=k} (s_i / s_1)^{4}}{\sum_{i} (s_i / s_1)^{4}} .
$$

Степень 4 гасит «массу» больших категорий: на отложенной выборке (2000 СТЕ) верная категория первой в 74 %
против 66 % у простой суммы. Кандидаты — категории с долей не меньше $0{,}15 \cdot \max \mathrm{share}$, не
больше шести; список входит в RRF с весом 2. Если больше всего голосов у класса «не товар» (работы,
услуги), позиция товаров была бы чужой — кандидатов нет. В интерфейсе доля голоса — «Совпадение N %»
(округление вниз) и до двух похожих СТЕ с картинкой. Английские слова, которых нет в наименованиях СТЕ,
расшифровывает словарь («wheels» — колёсные диски).

### 2.5. Выбор категории без вопроса

Категория с $\mathrm{share}(k) \ge 0{,}7$ — единственный кандидат, шаг выбора категории пропускается
(решение команды 07.10). Доли в сумме дают 1, поэтому выше порога бывает одна категория; ниже — выбор из
нескольких с процентами. Цена порога на отложенной выборке:

| Порог | Решено без вопроса | Неверно среди решённых | Неверно от всех |
|---|---|---|---|
| 0,5 | 60,9 % | 21,6 % | 13,2 % |
| 0,6 | 50,9 % | 18,2 % | 9,2 % |
| 0,7 | 41,2 % | 14,6 % | 6,0 % |
| 0,8 | 30,3 % | 11,0 % | 3,4 % |
| 0,9 | 19,0 % | 6,6 % | 1,2 % |

(справочник 8 569 категорий, отложенная выборка 2 000 СТЕ, 08.10). Ниже 0,7 ошибок прибавляется быстрее, чем
решений. Второй сигнал из локальной модели не помог: `qwen3.5:9b` на 300 СТЕ с долей 0,4–0,7 выбирает из пятёрки
верно в 53,9 % (первая по голосу — 59,3 %), а при согласии с голосом верна в 72,3 % — ниже 85 % нынешнего

проиграли), код ставится только после подтверждения позиции.

## 3. Извлечение и приведение значений

### 3.1. Правила, затем LLM

Описание режется на фразы по строкам, «;», точкам и запятым. Для характеристики $c$ ищется фраза с её меткой
(имя характеристики или синоним) и значение в той же фразе: число с единицей после него, значение из перечня
$V_c$, слово-признак. Число со счётной единицей («50 шт») не попадает в физическую характеристику; единица
другой величины означает, что число относится не к этой характеристике.

Значение перечня в тексте совпадает целым словом, по основе прилагательного или по основе слова от 4 букв;
приставка числа вид не меняет: «однорычажный» — это «Рычажный», «двухвентильный» — «Вентильный» (так
различаются позиции КТРУ смесителей), но «полуавтоматический» — не «Автоматический». Перечни позиций КТРУ
одной категории сливаются: у каждой позиции он свой. У кандидатов-категорий — нет: чужие значения других
категорий снижали полноту заполнения (43,6 → 42,2 % на отложенной выборке).

Метка сверяется с именем характеристики и с её синонимами (портала и склейки дублей): «Предназначение» —
метка «Назначения». При равенстве совпадение по имени важнее совпадения по синониму (вес синонима 0,99).

Что правила не нашли, спрашивается у LLM с JSON-схемой `{"items": [{"name", "value", "unit", "quote"}]}`, —
только о характеристиках позиции с определённым кодом (в `/autofill`, если код определён сразу, иначе в
`/answer`, когда его определил ответ) и не дольше $T = $ `LLM_BUDGET_S` (4 с): не успела — карточка без неё.
Отказ сервиса (квота, 429, сеть) ставит модель на паузу 2 мин; плохой вход одного поставщика (400, NaN) — нет.
Ответ модели — гипотеза, её проверяет код: элемент принимается, только если имя есть среди $C(p)$, цитата
`quote` дословно есть в тексте и содержит значение (числа совпадают, слова — с той же основой). Значения от LLM
код КТРУ не выбирают (раздел 4).

### 3.2. Подгонка значения к спецификации

Для количественной характеристики значение $v$ с единицей $u$ переводится в единицу позиции:
$v' = v \cdot \kappa(u \to u_c)$, где $\kappa$ — множитель из таблицы единиц одной величины (мл → л, кВт → Вт,
мм → мкм, м³ → л, ГБ → ТБ…). Разные величины ($\kappa$ не определён) — статус `unit_mismatch`, значение не
ставится. Затем:

$$
\mathrm{fit}(v') =
\begin{cases}
\text{вне диапазона}, & v' \notin [lo_c, hi_c],\\
\text{корзина } b, & \exists\, b \in V_c:\ v' \in b \ (\text{«≥80 … <90»}),\\
\text{не из перечня}, & V_c \ne \varnothing \text{ и корзины нет},\\
v' & \text{иначе.}
\end{cases}
$$

Множитель $\kappa \ge 10^6$ или $\le 10^{-6}$ («5 мВт» при «МВт») — не значение, а «проверьте единицу»: так
выглядят описки и ошибки шаблонов (у красной лазерной указки на портале «МВт; 10³ кВт»). Приставки м и М
различаются регистром (мВт — милливатт, МВт — мегаватт); «градус» без уточнения — угол или °C по имени
характеристики («Угол наклона» — °, «Температура хранения», «Условия хранения» — °C).

Проверка на живых СТЕ портала (2 % выгрузки, 260 088 значений поставщиков против характеристик их
категорий; код и справочник до 08.10 против нынешних): ложных «единица не подходит» на верных данных было
22 255, стало 4 717 (−79 %): «Л; ДМ3» и «см³; мл» — единица по любой части через «;», м³/ч, Мбайт/с,
«млс», Ом, л. с., кВт·ч, «° градус»; точных совпадений 225 971 → 243 667. Извлечение из текста на
5 530 СТЕ: +38 значений, −1.

Рядом со значением показывается та же величина короче: $\arg\min_{u \in U(q)} \bigl(|\mathrm{fmt}(v' \kappa(u_c \to u))|
+ |u|\bigr)$ по общепринятым единицам величины $q$ (мм, см, м, км; мг…т; мл, л; мВт…МВт; …), только при точном
пересчёте (не больше трёх знаков после запятой), при равной длине — своя единица: 1500 мм → «1,5 м»,
1000 кВт → «1 МВт», 0,15 м → «15 см». Значение остаётся в единице позиции.

Для качественной: точное совпадение → совпадение после свёртки (регистр, `ё`, латинские двойники) →
ближайшее допустимое по Левенштейну (опечатка, от 5 букв, однозначно) → «не из перечня» со списком допустимых.
Расстояние считается не дальше двух правок: перечни бывают из длинных текстов (составы), полный счёт стоил до
194 с на карточку.

### 3.4. Подсказки похожих СТЕ

Когда код $p$ определён, для характеристик без значения из текста и модели берутся $N = 10$ похожих СТЕ той же
категории (BM25 по наименованиям, индекс без отложенной выборки при оценке). Пусть $W_c$ — значения
характеристики $c$ у тех из них, у кого она заполнена (по имени или синониму), подогнанные к $c$ (раздел 3.2;
не подошло — голос против). Подсказка — $v^* = \arg\max_v n(v)$, если $n(v^*) \ge 2$ и
$n(v^*) / |W_c| \ge 0{,}6$. «Общие сведения» (производитель, страна) не подсказываются. В карточке подсказка
помечена `method: "similar"` и «как у $n$ из $|W_c|$ похожих СТЕ портала с этим полем — проверьте»; если всё заполнено из
текста, мастер сразу открывает проверку, с подсказками — шаг характеристик.

### 3.3. «Общие сведения»: производитель и страна

Это поля карточки, а не характеристики: перечень у них — подсказка (до 50 самых частых производителей и
стран категории по СТЕ), а не ограничение; детектор и минимум «4 характеристики» их не считают. Из текста
значение берётся по метке («Производитель: …») или, если метки нет, из наименования — только целым словом
или фразой из перечня, не меткой «X:», не словом имени характеристики, не значением другой характеристики
(«ЭВА» — материал) и не кириллическим словом в нижнем регистре («марка», «щепа»: в перечнях заводов бывают
нарицательные слова). Значение — в написании поставщика. Точность против карточки портала на 10 151 СТЕ
отложенной выборки (`app.tools.evaluate_general`): производитель 83,5 % (2 428 из 2 909; неверные — в основном
бренд вместо юрлица, BRAUBERG при САМСОН-ОПТ), страна 83,3 %.

### 3.5. Такая СТЕ уже есть: двойники

Модератор отклоняет заявку с причиной «Предложена другая СТЕ», если в каталоге уже есть СТЕ с теми же
наименованием и характеристиками (база знаний портала, статья 214102). Двойник новой карточки — СТЕ портала с тем
же ключом наименования (`fold`, знаки препинания и кавычки — пробелы) или с той же моделью: слово наименования с
буквами и цифрами от 4 знаков, не размер («800х500х500», резьба «М10х50», шина «205/55R16») и не число с единицей
(«80г/м2», «220В»); ключ модели больше чем в двух категориях — признак, а не модель («IP65», «USB3»), а картридж
CE285A в двух категориях (215 СТЕ) — модель. Индекс — 3,7 млн СТЕ выгрузки портала
(`app.tools.build_twins`, sqlite ~4 ГБ, характеристики сжаты).

- **Категория.** Если доля двойников по наименованию в одной категории не меньше 0,7 (двойник из категории не из
  справочника голосует против), она — единственный кандидат, вопрос о категории пропускается.
- **Значения.** Поля без значения из текста берутся из двойников по наименованию этой категории: значение
  подогнано к позиции (раздел 3.2), хватает одного двойника, у нескольких — согласие не меньше 0,6 заполнивших
  поле. Порядок источников: ответ на вопрос, текст (правила, модель), двойник, похожие СТЕ (3.4). Если описания
  нет и текст — одно наименование (оно у двойника то же), о полях двойника модель не спрашивают: шаг быстрее и без
  квоты. С описанием модель сначала читает его обо всём, чего не нашли правила, а двойник заполняет остаток —
  значение поставщика важнее. Поле, о котором поставщик ответил («нет такой характеристики», «Другое значение»),
  подсказкой не заполняется. В карточке — `method: "twin"`, «как у такой же СТЕ №… на портале».
  Из «Общих сведений» — только производитель (без формы собственности, согласие не меньше 0,6): на 771 СТЕ
  выборки с двойником он верен в 91,6 % (по наименованию — 83,5 %, раздел 3.3), страна двойников — лишь в
  63,5 %, её не подсказываем.
- **Замечание** «Такая СТЕ уже есть на портале: №…» (`warn`, вид `duplicate`) — в ответе `/autofill` и в `/check`,
  если двойник по наименованию в той же категории; в мастере над полями — ссылки на эти СТЕ, пока проверка видит
  дубль (поправил наименование — блок уходит вместе с замечанием).

Двойники по модели — только в ответе API (`twins`, `by: "model"`): в мастере их нет, у болтов одного размера и
картриджей к одному принтеру модель общая, а товары разные. Выигрыш метрик ниже — на карточках, у которых такая
СТЕ уже есть, и для них же модуль предупреждает о дубле: польза — в том, что поставщик узнаёт о дубле до
отправки, а не через отказ модератора, и берёт её значения, если его товар отличается немногим (указав отличие),
а не в том, чтобы дубли создавались быстрее. На отложенной выборке (2 000 СТЕ; при оценке все 40 305 СТЕ выборки из
индекса вычтены, их двойники остаются — как у новой карточки на портале) двойник по наименованию есть у 15 % СТЕ,
только по модели — у 12 %. Решение категории по модели: из 82 прежде нерешённых СТЕ верно 23, неверно 59 (модель
из наименования — «KC-55713», «DC-60» — бывает у чужого товара); по наименованию — 145 верных из 175. Точность
значений: один двойник по наименованию — 94,4 % (391 из 414), несколько — 90,8 %, один двойник по модели — 58,8 %
(ниже подсказок похожих СТЕ, 80 %).

## 4. Сужение до конечного кода

Пусть $K$ — известные значения (из текста и ответов), $P_K = \{p : \forall (c, v) \in K,\ v \text{ подходит } c \text{ у } p\}$.
Кандидаты — не только двадцатка поиска: если все они одноимённые (поиск их не различил), в $P$ идут все
позиции с этим наименованием (`Catalog.same_name`, до 300). Иначе среди 100 перчаток, отличающихся одной
толщиной (`app.evaluation.near_twins`, блокер команды 06.10), «75 мкм» находило свою позицию лишь при
случайном попадании в двадцатку — 200 из 300 текстов; теперь 300 из 300, чужой соседней ни разу, а без
толщины в тексте модуль спрашивает о ней (строки `lookalike_*` на «Метриках»). Золотой набор не изменился.
Код ставится, когда $|P_K| = 1$. Иначе модуль задаёт один вопрос — характеристику $c^*$, которая в среднем
оставляет меньше всего позиций:

$$
c^* = \arg\min_{c}\Bigl(\neg\,\text{есть у всех},\ \ \frac{1}{|O_c|}\sum_{o \in O_c} |P_{K \cup \{(c, o)\}}|,\ \
\neg\,\text{обязательная},\ |O_c|\Bigr),
$$

где $O_c$ — варианты ответа: значения перечней кандидатов (и «нет такой характеристики», если она есть не у
всех). Вопрос, где выбирать не из чего или ни один вариант ничего не отсекает, не задаётся. Средний остаток, а
не энтропия разбиения: перечни позиций пересекаются («A4» есть у нескольких), разбиение — не разбиение.
Каждый вариант показывает, сколько позиций останется. Варианты, после которых остаются все позиции (значение
есть у каждого кандидата), сводятся в один «Другое значение»: ответ им ничего не отсекает, модуль задаёт
следующий вопрос. Последний вариант — «Ничего не подходит» (честный отказ). Ответ из вариантов сравнивается с
перечнем без исправления опечаток: «Желтый» — не «Белый» с ошибкой.

### 4.1. Категория, затем позиция КТРУ

Сужение идёт в два этапа: сначала категория (позиция справочника стандартов), затем позиция КТРУ среди
тех, на которые ссылаются характеристики категории (`chain.ktru`). Второй этап — то же правило $c^*$ по
характеристикам самих позиций КТРУ; известные значения — из текста (правилами, без LLM) и из ответов.
Ссылок у категории нет — «нет в КТРУ» (у 5 446 из 8 569 категорий стандарт портала на КТРУ не ссылается;
у остальных 3 121 позиции КТРУ загружены целиком);
ссылки есть, а позиций нет в справочнике — «нет в справочнике». Значение из возвращённой заявки или строки
файла, совпадающее с вариантом вопроса, отправляется ответом само, один раз на вопрос.

### 4.2. Подтверждение позиции

Код без подтверждения не ставится, если сомнение измеримо: позиция найдена ниже порога только по главному
слову, главное слово есть лишь в значениях позиции, позиция — запчасти к самому товару, в наименовании есть
слова о товаре, которых нет у кандидатов. Тогда вопрос «Позиция КТРУ»: подтвердить или «Ничего не подходит».

## 5. Детектор ошибок

Замечание — пара (правило, обоснование). Источники:

- перенос правил модерации портала (`checks/moderation.py`, сверка с прототипом на 13 тыс. вызовов);
- значение против спецификации (раздел 3.2): не из перечня, вне диапазона, единица не той величины, опечатка с
  исправлением;
- противоречие наименованию: качественное значение — другое значение перечня в наименовании; число — число
  той же характеристики в наименовании $x$ и в поле $y$ после приведения к единице позиции расходятся как ошибка
  ввода: $\frac{|x - y|}{\max(x, y)} \le 0{,}2$ (опечатка в цифре) или $\frac{\max}{\min} \approx 10^k$, $k \in \{1,2,3\}$, с
  точностью 2 % (перепутана единица: мл и л). Значение поля, которое в наименовании стоит у другой
  характеристики (длина и ширина переставлены), замечанием не считается. На 3 380 карточках портала с позицией
  правило дало 18 замечаний, из них ложных 1–2 («Машина стиральная … 6 кг» — загрузка, а не вес);
- гигиена: персональные и контактные данные (телефон, почта, паспорт, СНИЛС, ИНН, номер карты — с проверкой
  контрольной суммы Луна), мат, повторённые и пустые характеристики.

Уровень `block` запрещает отправку, `warn` — подсказка.

На 494 СТЕ, чьи категории есть в обоих справочниках, больший справочник ошибается чаще (первой 62,3 % против
67,0 %, среди пяти 76,7 % против 80,8 %): у товара больше похожих соседних категорий («Зерно пшеницы» и
«Корма для парнокопытных»). Покрытие это перевешивает: три четверти товаров меньший справочник не знает.

Порог $\theta$ выбирается перебором в `app.tools.evaluate`: для каждого $\theta$ считаются доля честных
отказов $A(\theta)$ на товарах вне справочника и доля описаний $H(\theta)$, где эталонная позиция среди пяти
кандидатов; берётся $\theta^* = \arg\max_\theta \min(A(\theta), H(\theta))$, при равенстве — меньший $\theta$.
Худшая из двух долей, а не сумма: модуль, который отказывает всем или всем подставляет код, бесполезен.
Чужой код дороже отказа (отказ исправит модератор, чужой код пройдёт в каталог), поэтому вторая линия защиты —
подтверждение позиции при измеримом сомнении (раздел 4) и метрика «Без чужого кода рядом».

## 7. Выбор LLM

Модель — локальная `gemma-4-31b-it-Q8_0.gguf` в llama.cpp server (OpenAI-совместимый API), эмбеддинги —
`bge-m3-Q8_0.gguf` во втором экземпляре сервера; облачных API нет. Семейство выбрано замером на той работе,
которую модель делает в модуле, — дозаполнение характеристик, пропущенных правилами, на карточках портала с
эталоном поставщика (`app.tools.compare_models`). Мера — полнота и точность после проверки кодом (раздел 3.1),
задержка. Замер 04.10 (gemma4:31b из Ollama API): 49 % найденных значений при точности 78 % и 0,8 с против
38 % и 74 % у gpt-oss:120b; с файлом Q8_0 на карточках портала замер не повторяли. Подробности, таблица и
оговорки — `docs/model-choice.md`.
