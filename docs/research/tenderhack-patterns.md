# Как TenderHack ставит задачи и оценивает

Основа — четыре методички 2026 года, которые организатор выдаёт на старте (Москва 03.04, Пермь 13.03, СПб 21.05,
Нижний Новгород 09.09; лежат локально в `docs/tender_last/`, в git не идут), Положения и открытые источники.
Метки: **[RAW]** — сырой текст источника проверен (curl/PDF + поиск по тексту), **[SN]** — только сниппет поиска.
Собрано 30.09.2026.

## 1. Шаблон методички

Методичку для Казани выдадут на старте. Все четыре прошлые устроены одинаково:

1. **Ключевые задачи** — те же, что на странице города. Для Казани уже опубликованы: Т1–Т8 в
   [../tz/01-methodology.md](../tz/01-methodology.md).
2. **«Пользователь сервиса должен иметь возможность: 1) … 5)»** — пользовательские сценарии. Для Казани их пока
   нет. По ним проверяют демо, поэтому на старте их сразу разложить в чек-лист.
3. **Ограничения** — во всех четырёх дословно одни и те же:
   1. Решение работает на Linux и даёт веб-интерфейс.
   2. Работает «ИСКЛЮЧИТЕЛЬНО на серверах, контролируемых вашей командой»: полный запрет любых внешних API —
      поисковиков (Яндекс, Google, Bing) и LLM (OpenAI, Gemini, Claude и подобных).
   3. Запрещены low-code и no-code платформы.
   4. Открытые модели можно, но выбор должен быть «рациональным и соразмерным». Предпочтение — лёгким моделям с
      быстрым инференсом. Необоснованно тяжёлые модели «могут снизить итоговую оценку».
4. **Этапы защиты** (одинаковые):
   - этап 1 — презентация до 5 минут со схемой BPMN, второй участник параллельно показывает реальные кейсы;
     до 100 баллов;
   - этап 2 — ссылки на репозитории (или архив) с кодом и визуальной частью; защита топ-5: 10 минут презентации и
     10 минут вопросов; ещё до 100 баллов, суммируются с первым этапом.

   Итог — до 200 баллов. У топ-5 обычно 140–190, у остальных 20–95. Отсюда 178 баллов у победителя в скрытой
   таблице на странице Казани.
5. **Критерии оценки** — раздел 2.
6. **Материалы**: ссылка на датасет (Яндекс Диск), zakupki.mos.ru, UI-кит Портала поставщиков в Figma, инструкции
   портала. UI-кит из пермской и московской методичек:
   `https://www.figma.com/board/G64ZNZOpvILbIPYx8XVbxO/Portal-Postavshikov-(catalog)?node-id=1-1238`.
   Интерфейс в стиле портала — дешёвый плюс к «интуитивности».

## 2. Критерии по городам (100 баллов за этап)

| Кейс | Критерии |
|---|---|
| Москва, умный поиск | прототип **40**; семантический и морфологический поиск, синонимы, опечатки **25**; персонализация по истории и поведению **25**; обоснование метрик качества **10** |
| Пермь, обоснование НМЦ | интерфейс **10**; поиск сопоставимых позиций **25**; фильтрация, ранжирование, статистика цен **20**; точность и обоснованность расчёта НМЦ **35**; ручной ввод цены и документ **10** |
| СПб, цены с маркетплейсов | прототип **40**; корректность данных с трёх маркетплейсов **25**; бесплатные поисковики и неформализованные источники **25**; обработка запросов и удобство (синонимы, опечатки, регион, интерфейс, лимиты запросов) **10** |
| Нижний Новгород, ИИ-поддержка | прототип **40**; структурирование базы знаний и качество ответов **20**; маршрутизация по линиям поддержки и мат **10**; методика оценки специалистов **20**; интуитивность интерфейса **10** |

Закономерности:

- «Наличие работоспособного прототипа» — 40 из 100 в трёх кейсах из четырёх. Без прототипа проигрыш сразу.
- Каждая ключевая задача превращается в отдельный критерий весом 10–35.
- Интерфейс — около 10. «Методика» или «обоснование» — 10–20.

**Гипотеза для Казани** (проверить по методичке на старте): прототип 40; подбор и нормализация характеристик
~20–25; сужение до кода КТРУ ~15–20; ошибки с обоснованием ~15–20; интерфейс ~10.

## 5. Как решали похожие кейсы победители

- **Казань 2025, one-zero-eight** [RAW, github.com/one-zero-eight/hackathon-tenderhack]:
  - стек: эмбеддинги и кластеризация, Qdrant, FastAPI, Postgres, React/TS, docker compose;
  - значимость характеристики = coverage · (0,65 + 0,35 · entropy) · reliability(unique_ratio);
  - названия характеристик лемматизируются, синонимы склеиваются через union-find по Jaccard;
  - их SQL (`backend/tests/call_zakupki.py`) показывает модель данных портала: Sku → SkuCharacteristicValue →
    ProductCharacteristic (Unit → Okei) + CharacteristicValue (string / int / decimal / date / bool);
  - в датасете характеристики шли строкой вида «Имя:Значение Ед;…».
- **Москва 2024, MISIS Ginseng Strip** [RAW, README]: исправление орфографии; классификация «товар / работа /
  услуга» на CatBoost (accuracy 0,94); бренд и модель по словарю; категория через e5-small (top-4 за 372 мс);
  топ-10 характеристик категории по частоте; ОКПД2 и КПГЗ через reestr.mos.ru.
- Ещё одна команда Москвы 2024: rubert-tiny плюс saiga_mistral_7b с выходом в JSON [RAW, README].

## 6. КТРУ: что важно знать

- ПП РФ № 145 [RAW, base.garant.ru/71606930]: у позиции КТРУ есть код, наименование, единица по ОКЕИ, описание
  (характеристики), даты начала и окончания обязательного применения. Количественная характеристика задаётся
  конкретным значением, исчерпывающим перечнем, диапазоном (мин/макс) или неизменяемым значением; качественная —
  исчерпывающим перечнем. Заказчик обязан применять позицию, дополнительные характеристики — только с
  обоснованием.
- Код строится от ОКПД2: `XX.XX.XX.XXX-XXXXXXXX` [SN]. В пермских данных встречался «22.19.60.119-00000008»
  (8 цифр после дефиса). Один источник показывает 7 цифр: проверить на данных организатора.
- Выгрузка: FTP ЕИС закрыт с 01.01.2025, вместо него «сервисы отдачи информации» (токен через Госуслуги, SOAP
  `getNsiRequest`, справочник `nsiKTRU` в XML) [RAW / SN]. На хакатоне справочник даст организатор.

## 7. Официальные правила создания и модерации СТЕ

Инструкция портала «Инструкция по созданию оферты и СТЕ» от 04.06.2026 [RAW, zakupki.mos.ru/cms/Media/docs/]:

- выбрать можно только конечную категорию; набор характеристик подставляется по шаблону категории;
- рекомендуемые характеристики двух видов: из позиции КТРУ (для закупок по ч. 12 ст. 93 44-ФЗ) и из ЕАИСТ;
  значения выбираются из перечня, можно создать новую характеристику;
- правила модерации: **не меньше 4 характеристик; единица в отдельном поле; значение не повторяет название;
  в названии нет значения и единицы**;
- в упрощённой форме «блок «Характеристики СТЕ» будет заполнен модератором»;
- после массовой загрузки черновик уходит на модерацию, только когда характеристики вручную заполнены в каждой
  заявке;
- «Подобрать СПГЗ» ищет только точное совпадение характеристик;
- для закупок до 3 млн ₽ на ЕЭТП «СТЕ должна содержать в себе характеристики КТРУ».

Это готовый набор правил для нашего детектора ошибок: в обосновании ошибки можно цитировать нарушенное правило.

Сторонние отзывы: модерация до 5 рабочих дней, прямой связи с модератором нет, утверждённую СТЕ поставщик сам не
правит; расхождение наименования СТЕ и спецификации ведёт к отказам в приёмке [RAW, pro-ability.ru, 03.09.2025].
«Формирование каталога СТЕ» — в топе тем обращений в поддержку [RAW, t.me/Supplier_Portal/1390].

## 9. Выводы для нашей постановки

1. Прототип — 40 баллов: стабильное демо важнее широты. Демо-сценарии готовим под «пользователь должен иметь
   возможность» из методички.
2. Модели лёгкие по умолчанию: справочники, правила, лёгкие эмбеддинги. LLM — только там, где правила не
   справляются, с замером задержки и обоснованием выбора на слайде.
3. Значения только из перечней и диапазонов КТРУ, единицы по ОКЕИ, с учётом дат обязательного применения.
4. Сужение категории — по уровням (ОКПД2 → КТРУ) с уверенностью на каждом шаге. При неоднозначности —
   вопрос пользователю с вариантами и числом отсекаемых кодов.
5. Детектор ошибок опирается на официальные правила модерации и цитирует нарушенное правило.
6. «Золотой набор» с тремя группами: обычные описания, с опечатками, вне справочника. На его метриках строим
   математическую модель (п. 7.7 Положения).
7. Интерфейс в стиле портала (UI-кит из Figma), понятный без объяснений: его оценивают на обоих этапах.
8. Упаковка под внедрение: API в двух режимах (форма поставщика и очередь модератора), BPMN с дорожками,
   `docker compose up`. Чистый репозиторий к код-ревью топ-5.
